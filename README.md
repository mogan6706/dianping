# TravelGo 智慧旅游服务平台

## 项目描述

TravelGo 是一个面向旅游出行场景的前后端分离平台，用户可搜索酒店和景点、浏览旅行攻略、关注旅行达人、参与限时优惠活动并领取优惠券。项目围绕酒店服务、内容社区和营销活动三大核心场景展开，基于 Redis、RabbitMQ、Elasticsearch、WebSocket 等技术实现高并发活动、全文检索、多级缓存和实时消息推送能力。

## 所用技术

**技术栈**

SpringBoot、MySQL、MyBatis-Plus、Redis、Caffeine、RabbitMQ、Redisson、Elasticsearch、IK 分词器、WebSocket、Lombok、Hutool

**核心亮点**

- 登录认证：使用 Redis 存储登录态，解决多实例部署下的登录状态共享问题；通过拦截器实现登录校验和 Token 有效期刷新。
- 酒店服务：构建 Caffeine + Redis 二级缓存架构，结合逻辑过期策略优化热点酒店查询性能；引入 Elasticsearch 实现酒店名称全文检索，替代 MySQL 模糊查询，提高搜索效率和系统扩展能力；基于 WebSocket 实现优惠活动实时推送。
- 活动营销：基于 Redis + Lua 实现优惠券秒杀资格预检，原子化完成库存校验、用户去重和库存预扣；结合 RabbitMQ 实现订单异步落库，削峰数据库写入压力，提升系统吞吐能力。
- 订单一致性：采用数据库条件更新防止库存超卖，并使用 Redisson 分布式锁保证集群环境下一人一单，确保秒杀活动数据一致性。


# TravelGo 项目亮点难点

## 1. 登录认证：Redis 登录态 + 拦截器

**为什么用Redis替代Session？**

如果直接使用服务器本地 Session，多实例部署时会遇到 Session 共享问题：用户第一次请求落到实例 A，Session 保存在实例 A；下一次请求如果被负载均衡到实例 B，实例 B 读不到实例 A 的 Session，用户登录态就会丢失。

当前项目没有使用服务器本地 Session，而是使用 Redis 存储登录态。用户登录成功后，服务端生成一个随机 Token，把用户信息转换成 Hash 存入 Redis，key 为 `login:token:{token}`，并设置 30 分钟有效期。前端后续请求把 Token 放到 `authorization` 请求头中。

**还有其他解决方法吗？**

可以使用 Spring Session + Redis，把原本的 Session 统一托管到 Redis；也可以使用 JWT，把用户身份信息签名后放到客户端，由服务端校验签名。

当前项目采用的是普通随机 Token + Redis 登录态方案，不是 JWT。Token 本身不承载用户信息，只作为查询 Redis 登录态的凭证。

**说说你的登录流程？**

登录时先校验手机号和验证码。验证码正确后，根据手机号查询或创建用户，然后生成随机 Token，把用户摘要信息写入 Redis Hash，并设置过期时间。接口返回 Token，前端后续请求携带该 Token。

**怎么使用拦截器实现这些功能？**

系统中设置了两层拦截器：

第一层拦截器是做全局处理，例如获取Token，查询Redis中的用户信息，刷新Token有效期等通用操作。

第二层拦截器专注于验证用户登录的逻辑，如果路径需要登录，但用户未登录，则直接拦截请求。

**使用两层的原因？**

使用拦截器是因为很多接口都需要识别当前用户，可以在进入 Controller 之前统一解析 Token、加载用户信息并写入 ThreadLocal。当前项目使用两层拦截器：第一层拦截所有请求，负责解析 Token、刷新 Redis 过期时间；第二层只拦截需要登录的路径，负责判断 ThreadLocal 中是否存在用户。

*好处：*

职责分离：这种分层设计让每个拦截器的职责更加单一，代码更加清晰、易于维护

提升性能：如果直接在第一层拦截器处理登录验证，可能会对每个请求都进行不必要的检查。而第二层拦截器仅在“需要登录的路径”中生效，可以避免不必要的性能开销。

灵活性：这种机制方便扩展，不需要修改第一层的全局逻辑。

复用 ThreadLocal 数据：第一层拦截器已经将用户信息保存到 ThreadLocal 中，第二层拦截器可以直接使用这些数据，而不需要重复查询 Redis 或其他数据源。

**为什么要用 ThreadLocal？**

用户信息在拦截器中查询完成后，会保存到 ThreadLocal。

后续 Service、Controller 可以直接获取当前用户，而不需要层层传递 userId 参数。

请求结束后需要及时清理 ThreadLocal，避免线程复用导致用户信息串用。

## 2. 酒店服务：二级缓存 + 缓存问题治理 + Elasticsearch 搜索

**酒店详情缓存怎么设计？**

酒店详情属于典型的读多写少数据。项目中没有让每次查询都直接访问 MySQL，而是使用 Caffeine + Redis 做二级缓存：先查本地 Caffeine，本地没有再查 Redis，Redis 命中后回填本地缓存。

**为什么使用 Caffeine + Redis 二级缓存？**

Caffeine 是本地缓存，访问速度比 Redis 更快，适合缓存当前实例上的热点酒店数据，减少高频请求对 Redis 的访问压力。Redis 是分布式缓存，多实例之间共享数据，适合保存跨实例可见的热点数据。

因此查询链路设计成 `Caffeine -> Redis -> MySQL`。热点酒店详情优先命中本地缓存，本地没有再查 Redis，Redis 命中后回填 Caffeine；更新酒店信息时先更新 MySQL，事务提交后刷新 Redis 和本机 Caffeine，再通过 RabbitMQ 广播刷新其他实例的本地缓存。

Redis 中的热点酒店详情采用逻辑过期方案。缓存里保存酒店数据和逻辑过期时间，key 本身不依赖 Redis TTL 自动删除。应用启动时会把酒店详情预热到 Redis，避免逻辑过期方案冷启动时读不到缓存。请求发现数据逻辑过期时，先返回旧数据保证接口响应速度，再由抢到锁的线程异步重建缓存。

需要注意的是，单个酒店详情查询当前主链路依赖 Redis 预热；如果 Redis 中没有对应数据，会直接返回不存在。搜索接口拿到酒店 ID 后批量查详情时，会先查 Caffeine 和 Redis，未命中的 ID 再回源 MySQL 并写回逻辑过期缓存。

**逻辑过期为什么比互斥锁更适合热点酒店详情？**

互斥锁方案在缓存失效时，只允许一个线程回源数据库重建缓存，其他线程等待或重试。它的一致性更好，但在热点数据高并发访问时会产生等待，接口吞吐和响应时间都会受影响。

逻辑过期方案不会阻塞用户请求。缓存逻辑过期后，当前请求仍然先返回旧数据，再由抢到锁的线程异步重建缓存。它牺牲的是短时间的数据新鲜度，换来更稳定的响应速度和更高的吞吐能力，适合酒店详情这种读多写少、允许短暂旧数据的场景。

**缓存和数据库怎么保持一致？**

酒店数据以 MySQL 为准，缓存是加速层。更新酒店信息时先更新数据库，事务提交后刷新 Redis 逻辑过期缓存和本机 Caffeine，再通过 RabbitMQ 广播通知其他实例刷新本地缓存。

这个方案不是强一致，而是最终一致。它适合酒店详情这种允许短时间旧数据、但要求高并发读取性能的场景。

**缓存穿透、击穿、雪崩分别怎么处理？**

缓存穿透是查询不存在的数据，缓存和数据库都没有命中，请求会反复打到数据库。常见方案是参数校验、缓存空值或布隆过滤器。当前酒店详情主链路使用逻辑过期和预热，不依赖空值缓存；空值缓存只保留在互斥锁方案的注释代码里，属于备用思路。

缓存击穿是热点 key 失效后，大量请求同时回源数据库。项目中热点酒店使用逻辑过期处理：过期后先返回旧值，再异步重建缓存，避免大量请求同时打到 MySQL。

缓存雪崩是大量 key 同时失效，或者 Redis 整体不可用，导致流量集中打到数据库。项目中通过热点缓存预热、逻辑过期、Caffeine + Redis 多级缓存，以及逻辑过期时间增加随机偏移来降低风险；生产环境还需要配合 Redis 高可用、限流、熔断和降级。

**为什么用 Elasticsearch 优化酒店搜索？**

酒店名称搜索如果直接用 MySQL `like` 做模糊查询，数据量上来后性能会比较差，也不适合做复杂搜索能力扩展。

项目中使用 Elasticsearch 承接酒店搜索。MySQL 仍然保存完整业务数据，ES 只负责搜索索引；查询时通过 `multi_match` 在名称、区域和地址字段中检索，先从 ES 获取匹配的酒店 ID，再复用酒店详情查询链路获取完整数据。这样既降低了 MySQL 的模糊查询压力，也能复用 Caffeine + Redis 二级缓存。

酒店信息新增或修改后，事务提交后会同步刷新 Elasticsearch 索引，保证搜索数据与数据库最终一致。

**为什么 Elasticsearch 查询更快？**

Elasticsearch 底层基于倒排索引。传统数据库更偏向“记录 -> 字段内容”的查询方式，如果使用 MySQL `like '%关键词%'`，通常很难有效利用普通索引，数据量变大后容易退化为扫描。

倒排索引会提前建立“关键词 -> 文档”的映射关系。查询时可以根据关键词直接定位匹配文档，再返回对应的酒店 ID，因此比 MySQL 模糊查询更适合全文检索场景。

**为什么使用 IK 分词器？**

酒店名称、区域和地址属于中文搜索场景，Elasticsearch 默认分词器对中文文本的切分效果有限，容易影响搜索召回率和命中效果。

项目中使用 IK 分词器对酒店名称、区域和地址进行中文分词。索引阶段使用 `ik_max_word` 尽量细粒度拆分文本，提高召回率；查询阶段使用 `ik_smart` 做相对智能的分词，减少无效匹配。这样可以让“杭州西湖酒店”这类中文搜索词更容易命中相关酒店数据。

**缓存问题的通用定义和解决方案**

什么是缓存穿透，怎么解决？

定义：查询一个数据库中不存在的数据，Redis 没有命中，MySQL 也查不到，导致每次请求都会绕过缓存直接打到数据库。

解决方案：

1. 参数校验：例如非法 id、非法手机号等请求直接拦截。
2. 缓存空值：数据库查不到时，也向 Redis 写入空值，并设置较短 TTL，避免重复打到数据库。
3. 布隆过滤器：提前维护可能存在的数据 id，请求进来先判断 id 是否可能存在，不可能存在则直接返回。

当前酒店详情主链路采用逻辑过期和缓存预热，不依赖空值缓存。空值缓存属于互斥锁方案中的备用实现思路，目前没有启用；如果后续切回互斥锁方案，可以在数据库查不到数据时写入短 TTL 空值，降低恶意或重复无效查询对数据库的压力。

**什么是缓存击穿，怎么解决？**

定义：某一个热点 key 过期或失效，大量并发请求同时访问这个热点数据，导致请求集中打到数据库。

解决方案：

1. 互斥锁：缓存未命中时只允许一个线程回源数据库并重建缓存，其他线程等待后重试缓存，适合一致性要求较高的场景。
2. 逻辑过期：缓存中保存数据和逻辑过期时间，过期后先返回旧数据，再由拿到锁的线程异步重建缓存，适合热点数据、允许短暂旧数据的场景。
3. 热点 key 预热：系统启动或定时任务提前把热点数据写入 Redis，避免高峰期首次请求直接打到数据库。

互斥锁是时间换空间，优点是一致性较好、实现简单，缺点是并发下会有等待；逻辑过期是空间换时间，优点是响应快、吞吐高，缺点是需要预热，并且可能短时间返回旧数据。

**什么是缓存雪崩，怎么解决？**

定义：大量缓存 key 在同一时间或短时间内集中失效，或者 Redis 整体不可用，导致大量请求直接打到数据库。

解决方案：

1. TTL 加随机值：给缓存过期时间增加随机偏移，避免大量 key 同时失效。
2. 缓存预热：系统启动或业务高峰前提前加载热点数据。
3. Redis 高可用：使用主从、哨兵或集群，降低 Redis 整体不可用的概率。
4. 限流、熔断、降级：当缓存或数据库压力过大时，保护数据库不被瞬时流量打垮。
5. 多级缓存：本地缓存、Redis 缓存、数据库分层兜底，降低单点缓存失效带来的冲击。

## 3. 活动营销：Redis + Lua

**为什么是要用Redis+Lua？**

Redis执行一条命令的时候是具备原子性的，因为Redis执行命令是单线程的，不存在线程安全的问题，但当执行多条Redis命令时，就不是的了，我们把多条Redis指令放到Lua脚本中，Redis会把Lua脚本作为一个整体执行，保证了原子性，无需加锁，天然互斥。

我使用 Redis + Lua 实现限时优惠活动资格预检，是因为它能在一次原子操作中完成库存判断、用户去重、库存预扣和用户参与标记，避免了传统多命令方式的竞态条件。同时，Lua 脚本减少了网络开销，提升了性能，适合高并发营销活动入口。

**说说这一套流程？**（就是`seckillVoucher`方法）

先获取用户 ID 并生成订单 ID，再将活动券 ID 和用户 ID 传给 Lua 脚本执行资格预检。Lua 脚本只负责 Redis 层判断和预扣：返回 0 表示成功，-1 表示库存未初始化，1 表示库存不足，2 表示重复下单。预检成功后，Java 代码把订单消息发送到 RabbitMQ 队列，由消费者处理后续落库逻辑，最后返回订单 ID 给前端。

**为什么不用 Redisson 在入口加锁？**

活动入口流量可能达到几千甚至上万 QPS。如果每个请求都先获取分布式锁，会产生大量 Redis 网络交互，并且锁竞争严重，容易把入口并发能力压低。

Lua 脚本是在 Redis 内部一次性完成库存校验、用户去重和库存预扣，只需要一次网络请求，不需要反复加锁、解锁和等待锁释放。对于秒杀入口这种高并发、短逻辑的场景，Lua 原子脚本比入口分布式锁更轻量，性能也更高。

## 4. 订单一致性：条件扣减 + Redisson 分布式锁

**什么是超卖问题，怎么解决？**

超卖问题是指高并发下多个请求同时判断库存充足，并同时创建订单，最终导致实际卖出的数量超过库存。

项目中没有使用版本号形式的乐观锁，而是使用数据库条件更新兜底扣减库存：

`update tb_seckill_voucher set stock = stock - 1 where voucher_id = ? and stock > 0`

这条 SQL 把“判断库存是否大于 0”和“扣减库存”放到同一次数据库更新中完成。即使多个消费者并发处理订单，也只有库存仍然大于 0 的请求可以扣减成功，避免库存被扣成负数。

**为什么 Redis 已经预扣库存，数据库还要再校验？**

Redis + Lua 负责入口层预检，主要目的是把高并发请求挡在 Redis 层，减少数据库压力。但异步下单链路里仍然可能出现消息重复消费、手动补偿、异常重试等情况，所以数据库层还需要做最终兜底。

当前落库时做了两层校验：

1. 先根据用户 ID 和活动券 ID 查询是否已经存在订单，防止同一用户重复下单。
2. 再通过 `stock > 0` 条件扣减数据库库存，防止并发或重复消息导致超卖。

这样 Redis 负责高并发入口削峰，MySQL 负责最终数据一致性兜底。

**为什么还需要 Redisson 分布式锁？**

一人一单不能只依赖 JVM 本地锁。多实例部署时，同一个用户的请求可能打到不同应用实例，本地锁只能锁住当前 JVM，不能保证跨实例互斥。

因此异步创建订单时，项目按用户维度使用 Redisson 分布式锁：

`lock:order:{userId}`

同一个用户的订单创建逻辑会串行执行，不同用户之间互不影响。这样既能保证集群环境下一人一单，又不会把所有用户都阻塞在同一把大锁上。

**Redisson 分布式锁有什么特点？**

Redisson 分布式锁支持可重入和自动续期。

可重入是指同一个线程可以多次获取同一把锁，Redisson 底层通过 Redis Hash 记录线程标识和重入次数。

自动续期是指业务执行时间超过锁默认过期时间时，Watch Dog 会在当前线程仍持有锁的情况下自动延长锁时间，避免业务没执行完锁就过期。业务完成后再主动释放锁。

### 活动订单异步落库：RabbitMQ 消息队列

**为什么用异步下单?**

我们用jmeter测试，发现高并发下异常率高，吞吐量低，平均耗时高

如果整个活动下单流程串行执行，查询活动券、查询订单、减库存、创建订单这几步都要访问数据库。MySQL 本身并发写能力有限，再叠加分布式锁，整个业务耗时会变长，高并发下吞吐能力较弱。

**怎么进行优化？**

我们把限时优惠活动下单流程拆成两段：前半段用 Redis + Lua 做资格预检，后半段用 RabbitMQ 异步处理订单落库。

Lua 脚本负责在 Redis 中原子判断库存是否充足、用户是否已经下单，并完成 Redis 预扣库存和用户记录。预检成功后，接口立即把订单消息发送到 RabbitMQ，然后返回订单 ID，避免用户请求一直阻塞在数据库写入上。

RabbitMQ 消费者收到订单消息后，再执行业务落库：按用户维度加 Redisson 分布式锁，二次校验一人一单，扣减数据库库存并保存订单。这样可以把高并发入口压力挡在 Redis 和 MQ 前面，让数据库写入由消费者异步削峰处理。

当前项目使用普通队列接收活动订单消息，并配置死信交换机和死信队列。普通队列中的消息如果超时会进入死信队列，死信队列消费者当前也会走同一个 `handleVoucherOrder()` 入口进行补偿处理。生产环境下还可以进一步补充消息确认、失败重试、幂等消费和告警监控，保证异步下单链路的可靠性。
